# D1 风险、未知数与回退

> 状态：**规划**，2026-10-31；配套 `d1-plan.md` / `wps.md` / `posix-profile.md`。
> 用法：每个 WP 开工前读自己相关的风险项；每个里程碑评审时逐项确认“已退役/
> 仍开放/已触发回退”。**“先验证什么”是动作，不是描述**——每个风险至少有一个
> 可在 1 个会话内完成的探针。
> 评级：概率/影响各分 **高/中/低**；“先验证”列是 D1 早期必须做的实验。

## 2. 详细风险与“先验证什么”

### R1 POSIX / libc / 目标库移植

**描述**：D1-E1 要求 zlib/FreeType/FFmpeg/SDL2 “能编译并运行”。这不是四个
库，而是：一套 libc（newlib）+ crt/syscall stubs + 线程/信号/时间/浮点 +
autotools/configure 的交叉编译适配 + 每个库的 POSIX 依赖面。任何一层缺 API，
都会在 `configure` 或链接期炸；修起来往往是“补一个 syscall + 改 libc + 重编
三个库”的连锁。

**先验证什么（按顺序）**：

1. **S1**：newlib 4.x 用 clang/lld `--target=x86_64-elf` 构建出 `libc.a/libm.a`，
   链接一个 `printf` hello；记录构建时间、失败点、需要的补丁。
2. **S1b**：用该 libc 编 zlib，跑 inflate/deflate 测试向量；验证 `stdio/malloc/
   time` 够用。
3. **S1c**：FFmpeg `configure --target-os=none --arch=x86_64 --disable-everything
   --disable-x86asm` 是否能过；SDL2 `configure --host=x86_64-elf --disable-audio...`
   是否能过。**只做 configure + 编译一个 .c，不链接全部**。
4. 记录每个库需要的 POSIX API 清单，回填 `posix-profile.md`。

**触发信号**：S1 两个会话内仍不能产出 `libc.a`；FFmpeg configure 需要大量
Linux 专有假设；SDL2 无法在无 `/dev`/无 `pthread` 下配置。

**回退**：

- 首选 **picolibc**（newlib 的裸机分支，meson 构建，`_sbrk` 钩子清晰）；
- 再不行用 in-tree 最小 libc（D0 已有字符串/格式化代码可复用），但 D1-E1
  只保留 **zlib + FreeType + SDL2 最小**，FFmpeg 降级为“PNG/JPEG 解码”或
  移到 D2；
- 任何 D1-E1 缩减必须负责人签字，并同步 `d1-plan.md` §2/§6。

### R2 TLS / X.509

**描述**：TLS 是 D1 的“真实页面”门。风险不在“能不能连”，而在：
证书链验证（RSA/ECDSA、BasicConstraints、SAN/通配符）、有效期（RTC/NTP）、
熵（TLS 随机数）、TLS 记录层边界（截断/重放/坏 MAC）、以及 BearSSL 的阻塞
API 与非阻塞事件循环的适配。任何一项错了都可能是**静默接受坏证书**。

**先验证什么**：

1. **S2**：BearSSL 在宿主构建，连本地 `openssl s_server`，完成握手 + 回显；
   记录需要实现的 entropy/time/I/O 回调。
2. **S2b**：用本地 CA 生成“有效/过期/自签/错主机名/错签名”五类证书，
   验证拒绝路径；这是 3b 的出口前置。
3. **S2c**：`getrandom` 的熵评估（重复种子、RDRAND 缺失时的 DRBG），至少
   100 万次采样无重复/偏差告警。
4. **S2d**：非阻塞握手：把 BearSSL 的 `WANT_READ/WANT_WRITE` 接进 `poll`
   循环，验证不会忙等。

**触发信号**：证书链在 `example.com` 上失败但本地自签通过（信任库/链构建
问题）；握手偶发失败（熵/时间）；TLS 记录层 fuzz 出现越界。

**回退**：

- 改用 **mbedTLS**（TLS 1.2/1.3，API 更完整，体积更大）；
- 仍不行则 D1-E3 降级为“HTTP + 本地信任的 TLS”，真实站点矩阵缩到 1 个
  固定站点（负责人签字）；**不允许**关闭证书验证来“先跑通”。

### R3 真实硬件 / 固件 / ACPI / APIC / SMP

**描述**：D1-E5 要求一款真机。未知数：UEFI 固件是否允许自写 loader（Secure
Boot）、GOP 是否可用、ACPI 表是否完整、PCI IRQ 路由（`_PRT`/MSI）、PS/2
键盘是否存在、网卡型号（e1000e vs 82574L）、SMP INIT/SIPI 时序、以及机器
是否有串口调试。QEMU/OVMF 能验证大部分，但固件差异只在真机上暴露。

**先验证什么**：

1. **S3**：OVMF/QEMU 上 UEFI stub 启动到串口，打印 GOP 模式、RSDP、memmap；
   这是 5a 的预检。
2. **M1 内锁定机器**：记录型号/固件版本/CPU/网卡/键盘/显示/串口；做一次
   “UEFI shell 启动 + 串口输出”的最小探针（不要求 Aster 完整启动）。
3. **5b 预检**：在 OVMF q35 上解析 MADT/FADT/MCFG/HPET，打印 CPU/IOAPIC；
   真机上先只做“读表 + 打印”，不改 IRQ 路由。
4. **5c 预检**：QEMU 上 INIT/SIPI 启动 1 个 AP 到 `hlt`，再扩到全部 AP；
   真机最后做。

**触发信号**：OVMF 下 stub 都起不来；真机无串口/键盘；MADT 缺项；APIC
路由导致键盘/NIC 中断丢失；SMP triple fault。

**回退**：

- loader 改用 **Limine/GRUB**（UEFI 支持成熟），Aster 仍从 64 位入口启动；
  这不改变 D1-E5 的“真机”语义，只换引导层；
- 真机只保证 **GOP 显示 + 串口输入 + 网络**，PS/2/xHCI 键盘作为加分项
  （这会缩小 D1-E5，需负责人签字）；
- AP 不启动（UP only）必须负责人签字；D1-E5 降级为 OVMF 同样要签字；
- 换机型（优先有 PS/2 + Intel 网卡 + 串口的二手台式机）。

### R4 TCP 正确性 / 吞吐

**描述**：旧树 TCP 是同步单段在途，D1 要流式发送 + 重传 + 窗口。常见坑：
RTO 依赖 tick（0f 未完成时无法测）；乱序/重复 ACK 处理；TIME_WAIT 端口耗尽；
零窗口；`poll` 与阻塞 socket 的唤醒丢失；1 MiB 在 slirp 下的吞吐。

**先验证什么**：

1. 2b 开工前用旧树 oracle 的 8 项 TCP 回归做 host 单测（握手/乱序/校验和/
   RST/RTO/FIN/大传输/丢包注入）。
2. QEMU slirp + 宿主 echo 服务，先 64 KiB 再 1 MiB；记录重传/耗时。
3. 10% 丢包注入 + 乱序注入；确认完成时间有上界。
4. 端口耗尽/TIME_WAIT 复用测试。

**触发信号**：1 MiB 传输 >30s 或超时；丢包后不恢复；`poll` 唤醒丢失导致
TLS 握手卡死。

**回退**：缩接收窗/单段发送（牺牲吞吐保正确）；引入 **lwIP** 作为备选
（评估 1 个会话）；D1-E2 的 1 MiB 目标降到 256 KiB（负责人签字）。

### R5 浏览器 B0 范围 / 排版 / 字体

**描述**：B0 是“无 JS 的 HTML/CSS 子集”，但“子集”没有天然边界。排版
（行内/块/换行/空白折叠）、字体度量、图片尺寸、滚动、畸形输入，每一项都能
无限深入；真实页面还会引入未支持的标签/属性。

**先验证什么**：

1. **S4**：宿主原型解析 5 页语料 → DOM dump + 简单布局坐标；确认 4a/4b
   的技术路线和工期。
2. 固定 B0 子集清单（`d1-plan.md` §6.4 + `wps.md` 4a），任何新增标签/属性
   都要改文档，不允许“顺手支持”。
3. 先做本地语料像素基线，再做真实页面；真实页面只要求“可读/可滚动”，
   不做像素对比。

**触发信号**：语料布局返工超过 2 个会话；真实页面大面积乱码/重叠；畸形
输入触发 panic/越界。

**回退**：缩到“标题/段落/列表/图片/背景色 + 滚动”；放弃链接/表格/复杂
CSS；真实页面只验 1 个纯文本页 + 1 个带图页；D1-E4 的 5 页语料减到 3 页
（负责人签字）。

### R6 协作式调度 + pthread 死锁 / 饥饿

**描述**：D1 保持协作式（决策 D1-D），pthread 只在阻塞点切换。风险：
mutex/cond 实现错误导致永久阻塞；FFmpeg/SDL2 线程忙等导致主线程饿死；
`nanosleep` 精度不足；信号打断阻塞 syscall 的语义不完整。

**先验证什么**：

1. 1c 的 `futex` 单测：wait/wake 丢失、超时、多等待者。
2. 1d 的压力测试：8 线程 × 10k mutex/cond，10 分钟无死锁。
3. 1g 的 FFmpeg/SDL2 先按**单线程**配置跑通，再试多线程；多线程失败不阻塞
   D1-E1（库能编译 + 单线程运行）。
4. 用 `kill`/fault 打断阻塞线程，确认资源回收。

**触发信号**：压力测试卡死；FFmpeg 多线程不推进；`pthread_join` 永久阻塞。

**回退**：目标库全部按单线程配置（`--disable-pthreads` / `SDL_THREADS` 关）；
pthread 只保留“能编译/能创建”的最小实现；D1 明确“内核协作 + ring3 抢占
（WP5-0g）”的边界；内核抢占/多核调度留 D2。

### R7 FPU/SIMD 上下文 / ABI 回归

**描述**：D0 用户程序是 `-mno-sse -mgeneral-regs-only`，没有 FPU 状态。开
SSE 后：CR0/CR4 配置、FXSAVE 区对齐、上下文切换、用户栈 16 B 对齐、内核
不能碰 XMM。任何一处错都是 #UD/#GP 或浮点串值，且很难定位。

**先验证什么**：

1. 0e 的 SSE demo：单线程 `sqrt/float` 正确；两线程交替计算不同值。
2. 用户栈对齐检查（crt0 + 编译器）；`movaps` 不崩。
3. 内核镜像反汇编确认无 SSE 指令（`-mgeneral-regs-only` 仍生效）。
4. 现有 159 条 run-ng 全绿，确认 ABI 寄存器承诺不变。

**触发信号**：用户 #UD；多线程浮点结果串；shell/displayd 启动崩。

**回退**：仅对需要浮点的库开 SSE，其余用户程序仍 no-sse；FreeType 用整数
路径；FFmpeg/SDL2 若必须浮点则保留 SSE（这是 D1 的底线）；最坏情况把
FFmpeg/SDL2 移到 D2（负责人签字）。

### R8 8h/24h 浸泡 / 泄漏 / CPU 占用

**描述**：1h smoke 已经观察到“空闲仍占 ~99% 单核”，说明 idle 循环有问题；
D1 还有 fd/handle/port/shm/进程/线程/net 缓冲的泄漏面。8h 不是“跑得动”，
而是“指标不单调增长”。

**先验证什么**：

1. 6a 先在 M2 落地 `/run/stats` + 1h dry-run，别等最后补计数。
2. 0f 的 HLT idle 用宿主 CPU 采样验证 <10%。
3. 每个里程碑跑 1h soak；泄漏阈值（PMM free 漂移 <1%、fd/handle/port/shm
   计数不增长）在 6a 固定。
4. 故障注入在 6b 先小规模跑，再进 8h。

**触发信号**：1h 就出现单调增长；空闲 CPU >50%；心跳/命令响应变慢。

**回退**：缩 workload（只保留 shell + HTTP）；允许“8h 无崩溃但 CPU 高”需
负责人签字；泄漏修不完则把对应子系统降级为可选（如浏览器 reload 频率降低），
但 D1-E6 的“无单调泄漏”不能取消。

### R9 范围膨胀 / 并行冲突

**描述**：D1 的五个方向都容易“顺手加功能”；并行会话多，`build-ng.ps1`/
`syscall.[ch]`/`main.c` 是冲突热点。D0 已经发生过“提交扫入别的会话文件”的
事故。

**先验证什么**：

1. 每个 WP 开工前对照 `wps.md` 的“不做”清单；新增需求先改文档。
2. `build-ng.ps1` 单写者；`main.c` 追加独立块；ABI 号段只在 0a 改。
3. 每次提交前 `git status` 只包含本 WP 路径；用 `session-commit.ps1`。

**触发信号**：WP 改到允许路径外；两个会话同时改 build；ABI 号段被重排。

**回退**：暂停该 WP，拆成两个；冲突文件由 owner 统一合入；范围变更走
`decisions.md` + 负责人确认。

### R10 时间 / 熵 / 证书有效期

**描述**：TLS 证书验证需要正确墙钟；QEMU RTC 通常对，但真机 RTC 可能错；
无 NTP 时长期运行会漂移。熵不足会让 TLS 随机数可预测。证书信任库会过期，
D1 没有更新通道。

**先验证什么**：

1. 0f 的 RTC 读取与宿主时间差 <5s；连续 8h 漂移 <1min。
2. `getrandom` 的 RDRAND/RDSEED 路径与 DRBG 回退；重复种子测试。
3. 3b 的证书有效期边界（notBefore/notAfter）；系统时间错误时的错误信息。
4. 信任库固定哈希 + 构建日期；D1 不做在线更新（文档写明）。

**触发信号**：证书全部被判过期；TLS 随机数重复；8h 后时间漂移导致新连接失败。

**回退**：NTP 客户端提前到 D1（需新 WP，负责人确认）；信任库随镜像更新
（发布流程）；时间错误时明确报错，不静默忽略证书。

### R11 构建 / 工具链 / 第三方供应链

**描述**：newlib/FFmpeg/SDL2/BearSSL 都是第三方；Windows/MSYS 下的
autotools/configure 与 `x86_64-elf` 交叉编译容易踩坑；源码体积大，不能全
提交进 git；版本漂移会让证据不可复现。

**先验证什么**：

1. `third_party/` 采用“pin 版本 + SHA-256 + 补丁集 + 下载脚本”，不直接
   提交大源码；S1/S2 先验证构建。
2. CI（`-Quick`）只跑 host 单测；第三方构建在本地/缓存，记录日志。
3. 每个库的许可证文件入库；发布包附第三方清单。

**触发信号**：同一 commit 两次构建产物不同；补丁无法应用；CI 超时。

**回退**：固定容器/工具链镜像；减少第三方（FFmpeg→图片解码）；把大库
构建移出 CI，只保留产物哈希。

### R12 没有可用真机

**描述**：D1-E5 需要一台真实机器；如果 M1 结束仍没有，整个真机车道无法验收。
机器可能不支持 UEFI/PS/2/Intel 网卡，或没有串口。

**先验证什么**：M1 内确认机器型号/可用性；做“UEFI shell + 串口”最小探针；
记录固件版本。备选机型清单提前列好。

**回退**：借/买指定二手机；OVMF 降级（负责人签字）；把 D1-E5 拆到 D1.1，
D1 只发 QEMU 版（这会改变 D1 出口，必须明确记录）。

## 4. 回退决策树（简版）

```text
S1 newlib 失败?
 ├─ 是 → picolibc → 仍失败 → in-tree 最小 libc（D1-E1 缩到 zlib+FreeType）
 └─ 否 → 继续

S2 BearSSL 失败?
 ├─ 是 → mbedTLS → 仍失败 → 仅本地信任 TLS（真实站点矩阵缩到 1 个，负责人签字）
 └─ 否 → 继续

S3 OVMF 失败?
 ├─ 是 → Limine/GRUB 过渡 loader → 仍失败 → D1-E5 降级 QEMU（负责人签字）
 └─ 否 → 锁真机，5a–5d

TCP 1 MiB 失败?
 ├─ 是 → 缩窗口/单段 → 仍失败 → lwIP 评估 → 仍失败 → D1-E2 降到 256 KiB（签字）

B0 语料失败?
 ├─ 是 → 缩标签/CSS 集 → 仍失败 → 只保证本地 3 页 + 纯文本 HTTPS（签字）

真机 8h 失败?
 ├─ 是 → 缩 workload/修泄漏 → 仍失败 → 8h 无崩溃但 CPU 高（签字）或 D1.1
 └─ 否 → D1 发布
```

## 5. 明确登记的未知数

1. **newlib 在 MSYS/clang 下的交叉构建**：没做过，S1 才知道。
2. **FFmpeg/SDL2 对 `x86_64-elf` 的 configure 假设**：可能需要补丁，S1c 才知道。
3. **BearSSL 的非阻塞封装**：它的 API 偏阻塞，非阻塞状态机需要验证（S2d）。
4. **目标机型号/固件**：M1 才锁定；GOP/PS2/网卡/串口都是未知。
5. **APIC/IOAPIC 在目标机上的路由**：MSI 能否绕开 `_PRT`，5b 才知道。
6. **协作式 pthread 下 FFmpeg/SDL2 能否稳定**：单线程可回退，多线程不承诺。
7. **真实站点矩阵**：D1 只承诺 3 个页面；网站改版会让基线失效，用本地
   HTTPS 测试 + 固定 URL 快照（若允许）。
8. **8h 真机浸泡的机器占用**：需要连续 8h 独占，排期要负责人协调。
9. **证书信任库更新**：D1 无在线更新；过期后需重新发版。
10. **旧 32 位树的网络 oracle 与 64 位差异**：老代码的 32 位假设/全局变量
    可能比预期多，2a 先做 host 单测再上 QEMU。
